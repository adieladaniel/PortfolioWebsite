# Adiel's Portfolio — Architecture & Plan

Living document. Update this whenever a stage lands or a real design/architecture decision is made — this is the record of *why* the codebase looks the way it does, not just what it does.

Concept: the site is one continuous 3D "constellation timeline" — small dim nodes at the start (early academic years) growing into denser, brighter clusters toward internships/projects/now, with the camera physically flying through it on scroll. Explicit goal: must not read as a generic/AI-generated portfolio template.

## Stack

- **Vite + React 19 + TypeScript** (`npm run dev` / `npm run build` / `npm run preview`). React 19 is a hard requirement — R3F 9.x and drei 10.x peer-depend on it.
- **3D**: `three`, `@react-three/fiber`, `@react-three/drei` (used narrowly — `Edges` only so far).
- **Scroll engine**: `gsap` + its bundled `ScrollTrigger`.
- **State**: `zustand` — per-frame scroll progress lives here so `useFrame` loops can read it via `getState()` without triggering React re-renders.
- **Fonts**: `@fontsource/space-grotesk` + `@fontsource/jetbrains-mono`, self-hosted via npm (not a Google Fonts CDN link).
- **Styling**: CSS Modules + hand-rolled design tokens (`src/styles/tokens.css`). No Tailwind.
- **Type-check**: `npx tsc -b` (strict mode + `noUncheckedIndexedAccess`).
- Deploy target: **Vercel** (not yet wired up — Stage 7).

## Design tokens (`src/styles/tokens.css`)

- **Typography**: Space Grotesk (display + body), JetBrains Mono (data/labels/stats). Deliberately not Inter/Poppins/Manrope.
- **Color grammar — "warm ember"**: background `#120e0c`. Node/accent color is a 3-stop gradient — dim rust `#6b4a35` → amber `#e08a3e` → hot white-amber `#fff1de` — driven by a milestone's `brightness` (0 = earliest, 1 = now). Implemented in `src/utils/color.ts` (`lerpColorStops`).
- Sharp corners everywhere (`--panel-radius: 2px`), not rounded SaaS-style cards — deliberate choice, confirmed with Adiel.
- **`--color-text-secondary`/`--color-text-tertiary` brightened** (2026-07-17) from `#a89686`/`#6f6154` to `#c7b8a9`/`#9c8d7c` — the originals were low-contrast against `--color-bg` for body text sitting directly over the 3D scene (worst in Hero, which has no solid card behind its text). Same warm hue, meaningfully higher lightness, kept two visible steps below `--color-text-primary` so the hierarchy still reads. Single token-level change, propagates to every section automatically — chosen over Adiel's alternative suggestion of a multi-color theme, which would have fought the deliberate warm-ember identity built up over every prior stage. Hero's `.scrim` opacity also nudged up slightly as a second line of defense.

## Content/data layer (`src/data/`)

Raw content files hold only real copy, no geometry/camera concerns: `profile.ts`, `education.ts`, `internships.ts`, `projects.ts`, `skills.ts`, `codingStats.ts`, `certifications.ts`, `contact.ts`, all typed via `types.ts`.

**Ordering convention** (confirmed with Adiel): most-recent-first within every list — resume convention, not oldest-first chronological. Applies to `education.ts`, `internships.ts`, `projects.ts` as they render in the flat DOM sections.

`timeline.ts` is the single bridge between content and 3D:
- `timeline: Milestone[]` — ~11 hand-authored milestones (hero → prior schooling → CHRIST → Bank Management System → IEEE internship → ScholarSync → Edunext internship → skills → coding stats → certifications → contact), each with an `anchor` (3D spine control point), `scrollRange` (0..1 window it owns), `density`, `brightness`, `accentColor`, optional `lookAtOverride`.
- **Note**: the milestone spine itself is still old→now chronological (a deliberate "growth arc" — dim past to bright present) even though the flat-list ordering above is recent-first. This is an intentional, currently-unresolved divergence — see "Open decisions" below.
- `buildGraph()` → `graph: Graph` — procedurally scatters `density` decorative nodes around each milestone's anchor (seeded PRNG, `src/utils/prng.ts`, seeded by milestone id so it's stable across renders), connects k-nearest neighbors within each cluster, and chains one "spine edge" between consecutive cluster cores. Computed once at module load (it's static).
- `getMilestone(id)`, `findMilestoneAtProgress(progress)` — lookup helpers.

3D code never imports the raw content files directly (only `timeline.ts`/`projects.ts` for geometry-relevant fields) — editing a bullet point can't break the camera path, and tuning the spine can't corrupt copy.

## 3D scene & camera (`src/scenes/`, `src/store/sceneStore.ts`)

- **`CurveSpline.ts`** — `spineCurve`, a `THREE.CatmullRomCurve3` built once from the milestone anchors. The literal path the camera travels.
- **`sceneStore.ts`** — `targetProgress` (raw scroll progress, written by GSAP) and `progress` (damped/smoothed, written every frame by `CameraRig`). 3D components read `progress` via `getState()` inside `useFrame`, never as a React-subscribed value, so nothing re-renders 60x/second.
- **`CameraRig.tsx`** — the core mechanism:
  1. One `ScrollTrigger` (`scrub: true`, spans `document.body` top-to-bottom) writes raw scroll progress into the store on `onUpdate`.
  2. Every frame, damps a local ref toward that target via `THREE.MathUtils.damp` (frame-rate independent easing), writes the damped value back to the store as `progress`.
  3. Sets `camera.position` from `spineCurve.getPointAt(progress)`.
  4. Look-at defaults to a point slightly ahead on the curve; if the current milestone (via `findMilestoneAtProgress`) has a `lookAtOverride`, blends toward it with a **smoothstepped** triangular weight peaking at the milestone's scroll-range center — this is what makes the camera swing to frame a project object instead of just looking straight down the travel path. (Was a raw linear triangular weight — smoothstepped after Adiel reported the camera swing feeling mechanical/abrupt at the peak.)
  - **Camera path tuned down after Adiel reported it "moving way too much spiral or left/right."** Two changes: (1) `CurveSpline.ts`'s `CatmullRomCurve3` tension raised from the default 0.5 to 0.8 — tighter, less overshoot past each anchor; (2) the milestone anchors' x-zigzag amplitude in `timeline.ts` roughly halved (e.g. `±2`/`±2.5`/`±3` → `±1`/`±1.2`/`±1.4`) and the two project `lookAtOverride` points recomputed to match (same fixed offset from their anchor, `{2.6, 1.6, 1.2}`, as before). The curve still S-curves through 3D space — that was always the intent — just gentler.
- **`NodesInstanced.tsx`** (currently unplugged from the scene, see Runway below) — every graph node rendered as a `THREE.Points` glow-point cloud (`src/shaders/glowPoint.glsl.ts`: soft radial falloff via `gl_PointCoord`, additively blended), not lit spheres — one draw call for hundreds of nodes, built once since the graph is static. **Two bugs caught and fixed post-Stage-5:**
  1. *Nodes rendering as huge flat circles* (same category as the `ProjectObject` fix below, just never applied here): decorative nodes were scattered with `radius` allowed down to ~0, and the bright "core" node was placed exactly at `milestone.anchor` — a literal point the camera flies through — so nodes routinely rendered as huge flat-shaded circles blotting out text when the camera passed close. Fixed in `timeline.ts`'s `buildGraph()`: raised the minimum scatter distance from the anchor (`MIN_NODE_DISTANCE`), offset the core node off the exact anchor point in a seeded random direction (`CORE_OFFSET_DISTANCE`, same trick as `lookAtOverride`), trimmed max node sizes slightly.
  2. *Switching to point sprites for a proper "glow" look* (the flat lit spheres from fix #1 still didn't read as "nodes of light" per the original pitch) initially overcorrected into a blown-out white blob: the standard tutorial point-size formula (`size * 320/-z`) assumes objects tens of units from the camera, but ours can be as close as ~1.6 units (`MIN_NODE_DISTANCE`), so `gl_PointSize` was blowing up to thousands of pixels and additive blending stacked multiple such points into solid white. Fixed by recalibrating the distance constant, hard-clamping `gl_PointSize` to a sane pixel ceiling in the vertex shader regardless of proximity, and tuning per-cluster size multipliers down substantially — see `glowPoint.glsl.ts` for the clamp and the size-multiplier constants in both `NodesInstanced.tsx` and `CodingStatsCluster.tsx`.
- **`EdgesLines.tsx`** — a list of edges as one `LineSegments`/`BufferGeometry` (takes an `edges` prop; still used by `CodingStatsCluster`).
- **`ProjectObject.tsx`** — per-project shell-and-core object: an outer faceted icosahedron (translucent fill + `drei`'s `Edges`) around a smaller, brighter inner icosahedron core that counter-rotates against the shell — reads as a finished "energy core" object, not a bare wireframe. (Originally just the outer wireframe shell alone at very low opacity — Adiel wanted the sphere/globe-looking object to have "a cool face" too, not just lines; the inner counter-rotating core was the fix, in the same spirit as the building-shell fix below.) Scales from a small "distant node" up to full size as `progress` nears the project's milestone center. **Important**: the object is positioned at the milestone's `lookAtOverride` point, not its `anchor` — the anchor sits on the camera's literal flight path, so if the object were placed there the camera would fly *through* it. `lookAtOverride` is authored as an offset to the side of the spine specifically so the camera passes *beside* the object while looking at it. (This was a real bug caught and fixed during Stage 3 — see the fix note in `timeline.ts`'s project milestone comments.)
- **`Runway.tsx`, `RunwayCubeSwarm.tsx`, `RunwayCubeFill.tsx`, `RunwayBuildingShell.tsx`, `RunwayPath.tsx`, `runwayCubes.ts`, `runwayConstants.ts`** — replaces the abstract node/edge cloud as the primary visual, per Adiel's request (2026-07-17): a literal skyline connected by a continuous ground line (`RunwayPath`, built via `new THREE.Line()` + `<primitive>` — R3F's `<line>` JSX intrinsic collides with the DOM/SVG `<line>` type in this project's tsconfig, so the raw-object-plus-primitive pattern is required here specifically, unlike `<lineSegments>` which has no such collision). Each milestone's "building" is a **swarm of small wireframe cubes** that fly in from a scattered cloud and assemble into a stacked tower as the camera approaches — a direct reference to Ra.One (2011)'s "Q-Bricks" VFX sequence, where thousands of intelligent cubes assemble into a character (researched via web search — see chat history for sources). Per-milestone cube count/layers scale with `brightness` (more layers, more cubes for later/brighter milestones — the swarm gets more *complex*, not just taller), colors reuse the milestone's `accentColor`. Cube-building logic (positions, scatter, grouping) lives in `runwayCubes.ts`, shared by three rendering layers: `RunwayCubeSwarm` (one global `InstancedMesh`, wireframe shell, always visible), `RunwayCubeFill` (one `InstancedMesh` *per milestone*, solid material whose opacity ramps up with that milestone's assembly), and `RunwayBuildingShell` (one solid box + `Edges` + 3 floor-line accents *per milestone*, sized to the group's full `height`/`FOOTPRINT`, fading in only once assembly is >55% — the actual building facade). `NodesInstanced`/main-graph `EdgesLines` are **not deleted**, just unplugged in `ConstellationScene.tsx` — Adiel's framing was "depends on how well [the runway] can be built," so reverting or combining both is still on the table pending his review.
  - **"Just a few cubes with no real face" — fixed via `RunwayBuildingShell`.** The individual cubes (swarm + fill) still handle the assembling/materializing motion, but once a milestone crosses ~55% assembled, a single continuous solid-box facade fades in around the whole tower (own one-way ratchet, same pattern as the cube layers), with 3 thin horizontal floor-line meshes at evenly spaced heights for an actual architectural read. This is what makes the *finished* result look like one building rather than a loose pile of separate cubes with visible gaps. Facade rendering is a custom shader (`shaders/buildingFacade.glsl.ts`) — a procedural lit-window grid (dark mullions, ~50% of windows randomly lit per-window via a seeded hash, slow per-window flicker), not a photographic texture — deliberately kept in the same wireframe/glow procedural language as the rest of the scene rather than introducing the only photo-realistic asset in an otherwise abstract site.
    - **Debugging note — two independent bugs stacked on top of each other, both silent (no console errors).** (1) The seed hash used `fract(sin(dot(p, ...)) * 43758.5)`, the standard GLSL noise trick, but `p` includes `uSeed` (a per-milestone integer that can run into the hundreds from `hashStringToSeed(...) % 1000`) — `sin()` of a large argument loses essentially all precision under `mediump` (declared at the top of this shader), so every `cellSeed` silently collapsed toward the same value and every window came out "unlit." Fixed by switching to a `fract`-multiply-based hash that stays numerically stable regardless of the seed's magnitude — never feed a large, unbounded value into `sin()` inside a `mediump` shader. (2) Separately, the per-frame `uOpacity`/`uTime` updates in `RunwayBuildingShell.tsx` were mutating the `useMemo`'d uniforms object from the closure — but R3F's `applyProps` copies each uniform's *initial* value into a fresh object on the material at mount rather than keeping the passed-in object's reference, so the material's actual `uniforms.uOpacity` was a different object than the one being mutated every frame. The facade was rendering the whole time, at a permanently-stuck `alpha ≈ 0`. Diagnosed by logging `materialRef.current.uniforms.uOpacity === closureUniforms.uOpacity` (`false`) — fixed by reading/writing `materialRef.current.uniforms.*.value` directly inside `useFrame` instead of the closure object. **General lesson for any future custom `<shaderMaterial>` with per-frame-updated uniforms in this codebase: always mutate via the material ref's own `.uniforms`, never the object passed into the `uniforms` prop.**
  - **Layout reorganized from scattered zigzag to a clean two-row street.** Building X position used to be `milestone.anchor.x + side * LATERAL_OFFSET` — but `anchor.x` (tuned for the *camera's* path, see `CameraRig.tsx` above) varies by inconsistent amounts per milestone, so that inconsistency carried straight into building spacing and read as a scattered field (see Adiel's screenshot, 2026-07-17). Fixed by dropping the `anchor.x` term entirely: buildings now sit at a constant `side * LATERAL_OFFSET`, giving two straight, evenly-spaced rows (left side / right side) with only Z (already evenly spaced from Stage 3) and the gently-descending Y varying — `RunwayPath.tsx` updated to match so the connecting ground line stays consistent with where the buildings actually are.
  - **Assembly is a one-way ratchet, not raw proximity.** First version used `clamp01(1 - |progress - center| / span)` directly, which is symmetric — it fell back toward 0 once you scrolled *past* a milestone, so completed buildings disintegrated back into tumbling debris behind you instead of staying built. Fixed by tracking the max eased value ever reached per milestone group (`useRef<Float32Array>` in `RunwayCubeSwarm`, a plain `useRef<number>` per group instance in `RunwayCubeFill`) and taking `Math.max(previous, raw)` each frame — mirrors the same one-way philosophy as `Section`'s `IntersectionObserver` reveal. Confirmed via screenshots at late scroll depths: solid stationary clusters now, not scattered tumbling debris.
  - **Lateral offset increased (2.6 → 4.8 in `runwayConstants.ts`)** after Adiel reported swarms landing behind/under the DOM cards rather than in the open column beside them — the camera's forward-looking framing doesn't guarantee a fixed world-space offset maps to a consistent screen-space side, so pushing swarms further out was the pragmatic fix over attempting per-frame screen-space projection sync (which would fight against DOM sections being statically positioned per scroll range, not per-frame).
  - **Detailing pass (2026-07-18, Adiel: "the improvement on the building was good... I want more detailings to be added").** Three additions in `RunwayBuildingShell.tsx`/`buildingFacade.glsl.ts`: (1) floor count now scales with each building's actual `height` (`computeFloors`, `FLOOR_UNIT`/`MIN_FLOORS`/`MAX_FLOORS`) instead of a hardcoded 6, passed to the shader as a new `uFloors` uniform — a stubby early-milestone building reads as 2-3 floors, the "now" tower reads as 8-9, instead of every building squeezing/stretching the same fixed window grid; (2) a fresnel rim-glow in the fragment shader (`viewDir`/`cameraPosition` — auto-injected by three.js for `ShaderMaterial`, not `RawShaderMaterial`, no need to declare it) so facade edges catch the milestone's accent color at grazing angles, reading as glass curtain-wall rather than flat matte panels; (3) a thin rooftop antenna + pulsing beacon sphere per building (phase-offset per milestone via a hashed seed so they don't blink in lockstep), giving each tower a distinct skyline silhouette instead of a flat box top.
  - **"Card in view, but no building visible anywhere" — two compounding bugs, fixed 2026-07-18.** (1) **Z-depth framing.** A building's ground `Z` used to equal its own milestone's `anchor.z` exactly — but the camera is *also* at (or essentially at) that same `Z` when the milestone is most active (`progress == group.center`, card fully shown, swarm fully assembled), which puts the building almost directly to the camera's *side* — at or outside the edge of the 60°-FOV view frustum (`App.tsx`) — right when it's supposed to be most visible. Increasing `LATERAL_OFFSET` (the previous "fix," see above) couldn't actually fix this: pushing sideways from a point already beside the camera just pushes it further out of frame. Fixed by adding `FORWARD_BIAS_Z` (`runwayConstants.ts`) — the ground point is now pulled forward (more negative Z, in the direction of travel) by roughly 1.3x the ~4.5-unit inter-milestone anchor spacing, so the building stays *ahead* of the camera — inside the forward frustum, off to one side — for the whole time its card is on screen, only swinging beside/behind as the next milestone's card takes over. `LATERAL_OFFSET` was correspondingly brought back down (4.8 → 3.6) now that distance, not raw sideways push, is doing the framing work. (2) **Side/card mismatch.** `getMilestoneSide` alternated by raw `milestone.order` parity (0, 1, 2, 3…), but each section's DOM `align` (`src/sections/*.tsx`) doesn't alternate in lockstep with that — sections group multiple milestones under one fixed align (e.g. `education` covers order 1 *and* 2, both `align="left"`) — so several milestones (`christ-university`, `skills`, `coding-stats`, `certifications`) ended up on the *same* side as their own card purely by coincidence, landing the building behind/under it instead of in the open column. Fixed by deriving the side directly from a `CARD_ALIGN_BY_TYPE` lookup keyed to each milestone's `type` (matching the actual `align` prop each section uses) rather than order parity — the building's side is now always provably the opposite of its card's side. Verified via screenshots at every milestone's scroll-center: a building is now visibly in frame, on the correct side, for every section including the two that were worst-affected (Certifications, Coding Activity).
- **`JourneyAssembly.tsx`** — a small, separate set of ~14 cubes attached to the camera (repositioned every frame using the camera's world matrix basis vectors, parked in a fixed screen corner) that assemble based on *overall* scroll progress (0→1 across the whole page), not proximity to any one milestone — a persistent "how far through the journey am I" companion, visible from the very first frame, distinct from the per-milestone runway assemblies. Not ratcheted (unlike the runway) — it's a live progress indicator, not a record of a fixed past event, so it's allowed to reverse if the user scrolls back up.
- **`BackgroundShader.tsx`** + **`src/shaders/background.glsl.ts`** — a fullscreen `ShaderMaterial` plane repositioned every frame to sit a fixed distance in front of the camera, facing it (`camera.getWorldDirection` + copied quaternion), so it always reads as "the background" regardless of where the camera rig sends the camera. `depthWrite`/`depthTest` false + `renderOrder={-1}` so it never z-fights with real geometry. Fragment shader: a value-noise fbm haze (dark-biased), a soft glow following the damped cursor position (`useMousePosition`, a plain global `mousemove` listener so it works even where DOM covers the canvas), and color that shifts rust→amber→hot with `uScrollProgress` — same grammar as the node/edge colors. Shader color constants must be manually converted sRGB→linear (`pow(x, 2.2)`) before use, since the renderer's output encoding brightens raw fragment output — see the comment in that file.
- **`ConstellationScene.tsx`** — composes `CameraRig` + `BackgroundShader` + `Runway` + one `ProjectObject` per entry in `data/projects.ts` + `CodingStatsCluster`.

Rendering is fully unlit (`meshBasicMaterial`/raw `ShaderMaterial` throughout) — no scene lights. The aesthetic is "glowing points in the dark," not physically-lit objects, so lighting was deliberately left out rather than added and fought with.

## DOM layer (`src/sections/`, `src/components/`)

- `App.tsx` mounts the R3F `<Canvas>` `position: fixed; inset: 0; z-index: 0` behind everything, with all content sections in normal document flow above it (`z-index: 1`). One long scrollable page — no per-section pinning.
- **`HeroSection.tsx` redesigned full-bleed, three iterations** (2026-07-17, Adiel: "the creativeness with the cards or other things is highly missing"). No longer a boxed `GlassPanel` — huge kinetic name typography (`clamp(2.75rem, 6vw, 5.5rem)`), a `RoleTicker` cycling role labels every 2.6s, and a data-driven stat row (CGPA/problems-solved/internships/graduation year, all derived from existing `education`/`codingStats`/`internships` data, not hardcoded duplicates). `Profile` type gained a `roles: string[]` field for the ticker.
  1. First pass anchored everything to a `max-width: 46rem` left column — Adiel: "it's all leaning on the left side."
  2. Second pass tried to fix that by making the stat row `width: 100%; justify-content: space-between`, spreading it fully edge-to-edge — overcorrected; Adiel: "i didnt mean what you did right now... dont keep everything to either extreme left or extreme right."
  3. **Current version**: `.inner` is a real two-column CSS grid (`minmax(0,1.15fr) minmax(0,0.85fr)`, `max-width: 88rem`, centered) — text column on the left (name/role/headline/stats/bio, stats back to a compact wrapped row, not edge-spread), a `JsonProfileCard` (below) filling the right column. Both columns sit inside the section's own padding, neither touches the viewport edge. Collapses to a single column under 900px, card first.
- **`JsonProfileCard.tsx`** — a terminal/code-editor-styled card (macOS-style traffic-light dots + `profile.json` filename tab) that types out a real data object — `{ name, role, location, focus (pulled from `skills.ts`'s `ai-ml` category), cgpa, problems_solved, internships, status }` — as syntax-highlighted JSON, once scrolled into view. `tokenizeJson()` uses the standard regex-based JSON-highlighting pattern (matches strings/keys/numbers/booleans in one pass, keys distinguished from string values by a trailing `:`) to split the `JSON.stringify(data, null, 2)` output into colored tokens; a `revealed` character count (0 → full length) is used to slice each token's visible text in sequence, so formatting/indentation/newlines reveal progressively along with the content — not just a plain-text typewriter bolted onto pre-rendered JSON. Colors stay within the existing ember grammar (keys=amber, strings=hot, numbers=primary text, punctuation=tertiary) rather than introducing generic blue/green syntax-highlighting colors that would clash. **Bug caught and fixed**: the reveal was originally tick-count-based (`setTimeout` incrementing a counter by a fixed amount per call) — in practice this ran far slower than intended because the page's busy per-frame 3D scene (camera rig, cube swarms, background shader all updating every frame) competes for the main thread and throttled the `setTimeout` callbacks well past their nominal delay. Fixed by switching to elapsed-wall-clock-time-based progress (`requestAnimationFrame` computing `t = (now - startTime) / DURATION_MS`), which guarantees the reveal finishes within a fixed real-world duration (1.6s) regardless of how many frames actually fire.
- **Project/internship external links.** `Project.link`/`.repo` (already existed in the type) and a new `Internship.link` field now point to real GitHub repos Adiel provided (`ScholarSync` → `Student_Progress_Tracker-v2`, Bank Management System, the Edunext internship → `FinnBot-Financial-AI-Analytics-Engine`, the IEEE internship → `OncoVision`). `ProjectSection`'s expanded card shows a "view project/github ↗" link with `stopPropagation` so clicking it doesn't also toggle the card's collapse state; `InternshipSection` shows "view details ↗" when `link` is set. Never fabricate these URLs — always ask; wrong/invented links to someone's real GitHub are worse than no link.
- `Section.tsx` — shared wrapper used by every section except Hero. Adds a one-way `IntersectionObserver` reveal (fades/translates in the first time a section enters the viewport, then stops observing — doesn't re-hide on scroll-back). Respects `prefers-reduced-motion` (reveal is instant, no transition). Takes an `align?: 'left' | 'right' | 'center'` prop (default `'center'`, the old full-width behavior): `'left'`/`'right'` make `.section` a flex column (`align-items: flex-start`/`flex-end`) and cap **every** direct child — `SectionHeading`'s bar, its rule, and the content block alike — to `40rem` via `> *` (not just the content's `:last-child`), so the heading visibly sits on the same side as the card it labels, not stretched full-width while only the card shifts. `SectionHeading.module.css` deliberately has *no* `align-self` override anymore — it just follows the parent's `align-items` like any other child. **Two iterations to get here**, both from direct Adiel feedback: (1) first version pinned content to `var(--space-6)` from the physical viewport edge, leaving a stark empty gulf on the other side ("too much left and too much right") — fixed by nudging within the normal centered column instead of hugging the edge; (2) that fix only moved the content block, leaving the heading full-width and visually disconnected from its card — fixed by extending the same max-width rule to all of `Section`'s children. Alternated per section (Education=left, Internships=right, Projects=left, Skills=right, Coding Activity=left, Certifications=right; Contact stays `'center'` as a closing bookend, not part of the zigzag). Coding Activity overrides to a wider `46rem` via `:global(#coding-stats[data-align]) > :global(*)` in its own module CSS since its three-tier grid needs more room than the standard zigzag column.
- `GlassPanel.tsx` — translucent, blurred backdrop panel (`backdrop-filter: blur`) used everywhere text sits over the busy 3D background: Education/Internship/Project cards, Hero copy, Skills tag groups, Coding Activity stats, Certifications list, Contact block. This was a legibility fix made during Stage 3 review — bright "now" nodes were overlapping unprotected text before every section got this treatment.
- `SectionHeading.tsx` — the `NN / Title / dateRange` header every section uses; also carries its own blurred backdrop bar for the same legibility reason. **Now splits `title` into one `<span>` per character**, each fading/sliding in with a staggered `transitionDelay` (18ms × index) — its own self-contained one-way `IntersectionObserver` (not the parent `Section`'s, since that only tracks whole-section visibility and the animation needs to trigger exactly when the heading itself scrolls into view). Highest-leverage kinetic-text change in the codebase: because every section shares this one component, the effect appears everywhere automatically.

### Creative pass (2026-07-17, Adiel: "the creativeness with the cards or other things is highly missing")

Researched current award-winning portfolio sites (Awwwards portfolio winners, Bruno Simon's site) before making changes — see chat history for sources. The common thread: content *is* the interactive object, not decoration sitting on top of it. Three changes landed from that:

- **`CustomCursor.tsx`** — a dot + trailing ring (rAF loop, `lerp`-eased) replacing the system cursor on `pointer: fine` devices only (skipped entirely on touch). Grows and shows a label on hover of any `[data-cursor="label text"]` DOM element (project cards, contact links, the Codolio link), **or** when a 3D object sets `hoveredProjectId`/`hoveredTopicId` in `sceneStore` — the canvas has no real DOM elements to attach `data-cursor` to, so `ProjectObject` and `CodingStatsCluster` hovers reach the cursor via the store instead of the DOM listener path. `cursor: none` is applied globally via an `html.customCursorActive` class the component toggles on mount, not inline, so it only takes effect when the component actually mounts successfully.
- **Project cards now collapse by default** (`ProjectSection.tsx`) — name/tagline/tech visible, bullets hidden behind a CSS grid `0fr → 1fr` height transition — and expand when **either** the corresponding `ProjectObject` in the 3D scene is hovered (new `hoveredProjectId` in `sceneStore`, same cross-highlight pattern as `hoveredTopicId`) **or** the card itself is clicked/tapped (accessible fallback for touch and keyboard — the card is `role="button"` with an Enter/Space handler). This is the literal "3D object reveals the content" ask: the wireframe icosahedron isn't decorative anymore, it's the primary way to open a project. `ProjectObject` also scales up an extra `0.15` when hovered as feedback in the 3D view itself.
- **`CountUpNumber.tsx`** — counts from 0 to a target value once scrolled into view (own `IntersectionObserver`, one-way, ease-out cubic), applied to the hero's CGPA/problems-solved/internships stats and `CodingStatsSection`'s big total + per-language counts. Static under `prefers-reduced-motion` (jumps straight to the final value).
- **`MagneticLink.tsx`** — wraps an `<a>`, translates it slightly toward the cursor on `mousemove` within its bounds (no-op under reduced motion), snaps back on leave. Applied to all four Contact links.
